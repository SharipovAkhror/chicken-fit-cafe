# Правила работы AI-агентов

> **Это единый операционный контракт для любого ИИ-агента в репозитории
> [chicken-fit-cafe](https://github.com/SharipovAkhror/chicken-fit-cafe).**
> Неважно, какая модель и через какой инструмент запущена. Файлы `CLAUDE.md`,
> `GEMINI.md`, `GROK.md`, `.github/copilot-instructions.md` — тонкие указатели
> на этот файл. Логику держим только здесь.
>
> **Data class: client**  
> Приёмочная команда: `npm run build`
>
> Агенты сменяются. Не полагайся на память прошлой сессии: читай репозиторий.
> Стартовый handoff: [`STATUS.md`](STATUS.md).

Этот файл обязателен для всех AI-ролей и действует во всём репозитории. Более
специфичный контракт в `agents/*.md` дополняет, но не отменяет эти правила.

## 1. Иерархия источников

При конфликте используйте порядок:

1. Явное решение владельца проекта, зафиксированное в approved ADR.
2. Подтверждённые факты из `knowledge/facts/`, связанные с `confirmed` claim.
3. Approved-документ конкретной рабочей области.
4. Draft-документы и исследования.
5. Архив Gemini — только как источник гипотез, никогда как факт.

Конфликт уровней 1–3 **блокирует работу** и эскалируется системному архитектору
и владельцу проекта.

## 2. Протокол выполнения задачи

1. Работать только по issue с целью, владельцем, входами и критериями приёмки.
2. Проверить обязательные входы своего ролевого контракта.
3. Создать ветку `type/issue-id-short-description`.
4. Создавать артефакты со стандартными метаданными.
5. Обновить `knowledge/claims.yaml`, если появились или изменились утверждения.
6. Создать ADR, если решение влияет более чем на одну область, бюджет, данные,
   безопасность, архитектуру, бренд или необратимые действия.
7. Выполнить self-check и `node tools/validate.mjs`.
8. Передать результат на cross-review роли, которую он затрагивает.
9. Открыть PR по шаблону; человек утверждает критичные решения.
10. Обновить [`STATUS.md`](STATUS.md), если изменился handoff или фаза.

## 3. Метаданные документов

Рабочий Markdown-документ (кроме индексных README, шаблонов, STATUS и governance-файлов)
начинается с:

```yaml
---
title: "Название"
status: draft # draft | review | approved | superseded
owner: role-id
updated: YYYY-MM-DD
sources:
  - path/or/external-reference
---
```

Approved-документ обязан иметь непустые `owner`, `updated`, `sources`.

## 4. Жизненный цикл артефактов

`draft → review → approved → superseded`

- **draft** — рабочая версия, не источник истины.
- **review** — готово к проверке, изменения ограничены замечаниями.
- **approved** — утверждённый вход для зависимых работ.
- **superseded** — заменён новым документом; должна быть ссылка на замену.

AI-агент не может сам перевести критичное решение в `approved`. Это делает
указанный человек-approver в PR.

## 5. Именование и изменения

- Пути и имена файлов — `kebab-case`, язык содержимого — русский.
- Одна задача — одна ветка — один логически цельный PR.
- Не менять архив `archive/gemini/`.
- Не удалять подтверждённые факты; при устаревании создать новое утверждение и
  ADR, а старый документ перевести в `superseded`.
- Не хранить секреты, персональные данные, токены и договоры с чувствительными
  реквизитами в репозитории.

## 6. Обязательная эскалация человеку

- утверждение/отклонение названия, позиционирования и визуальной системы;
- бюджет, цены, маржинальность, найм и юридические обязательства;
- публикация, закупка, договор, платёж или внешняя коммуникация;
- обработка персональных/платёжных данных;
- конфликт подтверждённых источников;
- необратимое действие или неясные критерии приёмки.

Исключение: ведение уже созданного remote `chicken-fit-cafe` (commit/push/PR
по согласованному процессу) разрешено в рамках задач владельца; необратимые
операции (force-push, delete branch/repo, secrets) — только с явным «да».
